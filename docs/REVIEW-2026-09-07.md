## Prioritized findings

### 1. [P1] Restore the production visualization data

**Category:** reliability / operations. **Owner:** DRE Visualizations deployment.

Evidence and recovery are above. The homepage visualization is unusable, and Project Explorer also requests the missing manifest. Audit other generated-data surfaces after recovery rather than assuming they work because their headings render. Add a post-deployment health gate that resolves the manifest and verifies required artifacts before considering deployment successful.

### 2. [P1] Dashboard rendering loses the host's layout and title

**Category:** implementation integrity. **Location:** `../DREVisualizations/asset/js/dashboard.js:171–191`, `:37`, `:71`; `../DREVisualizations/view/common/block-layout/partials/dashboard-async.phtml:40`.

The template places `data-layout="collectionOverview"`, `data-title`, and `data-embed-slug` on the outer async container. `initAsyncDashboard()` now passes its inner `.rv-dashboard-content` to `renderDashboard()`, which reads layout and title from the passed element. The inner element has none of these attributes. Once data is available, the overview can use the dataset's generic layout/title and render statistics the curated overview intentionally omits. The same change also requires reviewing embed-button host lookup.

Pass explicit rendering options separately from the DOM destination, or retain a separate host argument. Add an executable async-render test with real wrapper markup that asserts the curated chart selection, title, and omitted duplicate statistics. Current source-contract checks pass despite this defect.

### 3. [P1] Failed dashboards disappear visually; library failures are swallowed

**Category:** accessibility / error handling. **Location:** `../DREVisualizations/asset/js/dashboard.js:174–195,222`; `../DREVisualizations/asset/css/dre-visualizations.css:1382`.

On JSON failure, the content is cleared and only `.rv-dashboard-status` is updated. That class is permanently clipped to a 1px box. This is confirmed live: the accessibility tree reports the failure while the screenshot shows empty space. Separately, `mountWhenVisible()` catches library-loader rejection with an empty function, so a failed library can leave the initial loading shell indefinitely.

Keep the persistent polite live region, but add a visible error state with a retry control and a useful search/browse link. Route both library and data failures through the same state handling. Preserve the original failure reason in diagnostic logging and isolate per-chart failures so one broken builder does not erase an entire dashboard.

### 4. [P2] Autocomplete accepts responses for obsolete input

**Category:** interaction correctness. **Location:** `../DRE-Search/src/svelte/components/SearchBox.svelte:69,88`; `../DRE-Search/src/svelte/components/SearchBar.svelte:75,123`.

Both components commit awaited suggestions without verifying that the input/request is still current. Clearing the input does not abort the outstanding request, and the fewer-than-two-characters branch returns before aborting. A slow response can therefore refill and reopen old suggestions after clearing. Abort alone also needs an identity guard, because the API converts abort errors into empty results.

Invalidate requests immediately on input change/clear, use a request sequence or captured controller identity after `await`, and test slow responses followed by clear, one-character input, and a newer query.

### 5. [P2] Smoke tests primarily verify shells, not completed behavior

**Category:** test architecture. **Location:** `tests/browser/search.spec.mjs:5`; `tests/browser/visualizations.spec.mjs:31`; `.github/workflows/live-smoke.yml`; `playwright.config.mjs`.

Most route checks stop after headings/main become visible and inspect errors synchronously. The asynchronous 404 on Project Explorer demonstrates the gap. The homepage also scrolls to the footer instead of its dashboard, making its lazy-load trigger dependent on page geometry. Traces and asset-version attachments are created locally, but the workflow does not upload them, losing the best failure evidence on runner cleanup.

Wait for each surface's meaningful ready/error state; scope chart assertions to the intended dashboard; scroll the dashboard into view; retain failed requests with URL/status. Upload failure traces, screenshots, and version attachments. Keep the existing read-only request policy. Add a small deterministic integration fixture for rendering failures rather than relying on production alone.

### 6. [P2] Mobile search delays the first result

**Category:** responsive design / visual hierarchy. **Location:** `../DRE-Search/src/svelte/components/FederatedApp.svelte:280,394`; theme interior masthead/content spacing.

At 390 × 844, the brand strip, whitespace, Search heading, query field, seven rows of corpus choices, Filters button, result summary, and wrapping action toolbar fill the viewport; no result is visible. The long brand title also truncates to “Africa Multiple Interactive Research…”. No horizontal document overflow was observed.

For narrow screens, use a compact, accessible corpus chooser with the selected corpus/count visible; consolidate secondary export/copy actions; reduce interior-page masthead spacing while preserving the homepage treatment. Keep the query, corpus, Filters, and result count easy to reach. Validate zoom, long French labels, keyboard use, and a populated filtered state before shipping.

### 7. [P2] Every header loads the complete search application

**Category:** performance / architecture. **Location:** `view/layout/layout.phtml:197`; `../DRE-Search/src/View/Helper/SearchAssets.php`; `../DRE-Search/src/svelte/main.ts`; `../DRE-Search/vite.config.ts`.

The header helper injects one IIFE containing SearchBar, App, and FederatedApp. Local committed assets are 160,570 bytes JS and 72,466 bytes CSS before compression. Record and informational pages pay for result/facet components to mount only a header typeahead. This is a measured bundle-size opportunity, not a measured Core Web Vitals failure.

Separate the header entry from full search, sharing the small API/i18n utilities. Load full search assets only on search surfaces. Preserve Omeka asset de-duplication, stable deployment paths, and the theme's fallback search. Compare transferred bytes and parse/execute cost before deciding the split is worthwhile.

### 8. [P2] Statistics cache stores locale-specific labels under a locale-independent key

**Category:** internationalization. **Location:** `helper/CollectionStats.php:60,77,239,284`.

The API fallback translates labels before caching the full array, but the cache key contains only version and site ID. Different visitor locales on the same site can receive whichever labels populated the one-hour cache. The precompute path also passes through source labels without translating them at render time.

Cache stable metric keys/counts and translate labels when rendering. If labels must remain in the cached payload, include locale in its key. Add a two-locale test using the same cached counts.

### 9. [P2] Homepage and search counts use different definitions

**Category:** information architecture / data contract. **Location:** `helper/CollectionStats.php:239–294`; visualization overview aggregation; DRE Search profiles.

Observed during this review: the homepage showed Locations **162** and Publications **559**, while federated search showed **205** and **562**. Different corpus definitions or refresh times can legitimately explain differences, but identical labels and destination links make them appear contradictory. Do not blindly force numeric equality.

Define each public metric once: scope, included resource types, public visibility, and refresh timestamp. Reuse that definition across stats, precomputation, and search, or make narrower metrics explicit in the label. Prefer configured IDs/profile definitions to duplicated title-based lookups. The API fallback currently hydrates up to 1,000 templates and item sets to resolve labels before making count queries; resolve only needed IDs and cache those mappings separately.

### 10. [P2] Long-lived pages can retain a pruned data generation

**Category:** cache lifecycle / resilience. **Location:** `../DREVisualizations/asset/js/dashboard-core.js:245–269`; `../DREVisualizations/src/Precompute/SnapshotPublisher.php:250–265`.

The browser memoizes the manifest for its entire page lifetime. The publisher keeps only two generations. A research page left open across enough regenerations can later request lazy data from a removed generation and receive a 404. This is a code-path risk, separate from the presently missing manifest.

On an artifact 404, invalidate the cached manifest and retry resolution once if its generation changed. Keep retries bounded and preserve public-data scope. Coordinate retention with expected page lifetimes without retaining revoked public data indefinitely.

### 11. [P3] Reduce competing titles and long prose lines on reading surfaces

**Category:** visual hierarchy / reading comfort. **Location:** `view/common/banner.phtml`, `view/layout/layout.phtml`, homepage Omeka page content.

The desktop record view has a strong item title, useful citation sidebar, and a working Mirador viewer. Above it, the full product name repeats in a prominent strip, while the mobile version truncates. The homepage's explanatory paragraphs span much of the desktop width, making long passages harder to scan.

Use a quieter compact identity treatment on interior pages and constrain prose blocks to a comfortable reading measure, leaving search and charts wide. Preserve institutional branding and factual copy. Treat this as a visual recommendation, not a functional defect or grounds for a redesign.
